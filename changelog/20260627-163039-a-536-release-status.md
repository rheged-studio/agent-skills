## Added

- **`release-status` skill** (`skills/release-status/`) — a read-only, advisory diagnosis of the release-please pipeline. It is a sibling of `send-it` (which stops at In Review), inspecting post-merge `main` and changing nothing.
- **Bundled `scripts/release-status.mjs`** (zero-dependency, Node built-ins only) gathers four signals via `gh` + `git` and prints a structured human report or `--json`:
  - **Version preview** — the bump and version the merged Conventional-Commit PR titles since the last tag imply (`feat`→minor, `fix`/`perf`/`revert`→patch, `!`/`BREAKING CHANGE`→major; `docs`/`chore`/`ci`/… cut no release), re-implementing the bump rules rather than importing `send-it`'s helper so the bundle stays standalone.
  - **Release PR** — the open `release-please--branches--main` PR and its required-check (`🔬 Build & Lint`) status.
  - **Stale `autorelease: pending` detection** — flags the recurring stall where the last merged release PR keeps the pending label and release-please aborts the next release, with the remediation surfaced.
  - **Tag-vs-version parity** — whether a `v<package.json version>` tag exists (clean no-op) or is missing (a publish is pending) — the `release.yml` version-vs-tag gate.
- **`--help`, `--json`, and `--self-test`** entry points; the self-test runs pure-logic assertions over the bump rules and the stale-label detector with no network or `gh` access.
- **`config.json` / `config.example.json`** exposing `mainBranch`, `releaseBranch`, `requiredCheck`, and `stalePendingLabel`, plus a `README.md` with install and usage.
- **vitest coverage** (`tests/skills/release-status/`) over the bump derivation, the stale-pending detector, and the tag-vs-version parity logic — all offline.
