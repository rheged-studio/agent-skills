@AGENTS.md

## Repo

Container for shared agent skills, distributed via [skills.sh](https://skills.sh). Each skill lives under `skills/<name>/` as a skills.sh-compatible bundle (with a `SKILL.md` manifest at its root); consumers install via `npx skills add` against this repo's URL.

The root package is `@rheged-studio/agent-skills` — **public and live** (`private: false`; flipped to public in the first release, `1.0.0`, and published on npm). Versioning is via **release-please** (Conventional Commits — ADR 0002, A-380), mirroring the setup in sibling repos `@rheged-studio/eslint-config` and `@rheged-studio/markdownlint-config`.

Architectural decisions live under `architecture/` as ADRs (sequentially numbered, immutable once landed). ADR-0001 (forthcoming — A-133) settles the deeper questions — skill directory layout, distribution conventions, semver discipline — that this bootstrap deliberately defers.

## Commands

```bash
pnpm install              # install deps (runs husky via the prepare script)
pnpm bootstrap:config     # materialise this repo's own skills/*/config.json from infrastructure/dogfood-config/ (A-615) — run once after clone
pnpm test                 # vitest — changelog + send-it helper unit tests
pnpm validate:changelog   # validate changelog/<ts>-<slug>.md entries (runs @rheged-studio/changelog-core validate)
pnpm validate:skills      # assert each skills/*/ package.json + SKILL.md metadata.version are consistent (A-364)
```

> **Per-skill `config.json` is generated, not tracked (A-615).** `skills add --copy`
> vendors every tracked file under `skills/<name>/`, so a tracked `config.json`
> would leak this repo's own values into consumers — only the neutral
> `config.example.json` ships. The gitignored `skills/<name>/config.json` is
> therefore regenerated by **two different paths depending on which repo you're in**:
>
> - **In _this_ repo (dogfood):** `pnpm bootstrap:config` materialises it from the
>   tracked `infrastructure/dogfood-config/<name>.json` tree (auto-run in CI and via
>   the `pre*` hooks of the scripts that read a config).
> - **In a _consumer_ repo:** `rheged-skills-setup` creates and reconciles it from
>   `config.example.json` + facts detected from the host repo.
>
> **To change a setting in _this_ repo, edit the corresponding
> `infrastructure/dogfood-config/<name>.json` and re-run `pnpm bootstrap:config`** —
> not the generated `skills/<name>/config.json` (it's gitignored and overwritten on
> the next bootstrap) and **not** `rheged-skills-setup` (that's the _consumer_ path; it
> isn't wired to the dogfood-config source). Changing a _consumer's_ setting is the
> other way round — see [`skills/rheged-skills-setup/SKILL.md#changing-a-setting-later`](skills/rheged-skills-setup/SKILL.md#changing-a-setting-later).

Versioning runs through **release-please**, driven by Conventional Commits. Under the dual merge policy (A-1176 / ADR-0005), **feature PRs** land as merge commits and the bump comes from landed **commit subjects**; **release-please version PRs** and **fan-out PRs** stay squash (orchestrator / fanout-spine). Both merge and squash remain allowed (A-1177). `pkg-release.yml` (via `reusable-pkg-release.yml`) publishes on a version-vs-tag gate.

Node 22 required (`.nvmrc`, `engines.node: ">=22"`, `engine-strict=true` in `.npmrc`).

## Conventions

- **Conventional Commits.** Commits follow `<type>(<scope>?): <subject>` (e.g. `feat(cleanup-repo): add stale-branch prune step`, `chore: bump tsx`). Local **pre-push** runs a best-effort commitlint range check (A-1023); the `commit-msg` hook still does not enforce Conventional Commits. The **PR title is CI-linted** by the standalone `validate-pr-title.yml` (a thin caller of `rheged-studio/shared-workflows`' `reusable-validate-pr-title.yml`, caller job id `pr-title`) — still required for humans and the completeness gate. Feature PRs merge via **merge commit**; release-please then ranks landed commit subjects for the bump (A-824). Squash remains for release + fan-out paths.
- **Draft PRs.** Open PRs as drafts by default; flip to ready when CI is green and the work is review-ready.
- **Dual merge policy (A-1176).** Feature / ship PRs → merge commits; release-please version PRs → squash (orchestrator); fan-out PRs → squash. Both `allow_merge_commit` and `allow_squash_merge` stay on (A-1177). For feature PRs, release-please reads landed Conventional-Commit **subjects** (`feat:` → minor, `fix:`/`perf:`/`revert:` → patch, `!`/`BREAKING CHANGE:` → major; `docs`/`chore`/`ci`/`refactor`/`test`/`build`/`style` cut no release). The PR title remains the CI/human declaration and should match the dominant type `/send-it` derives from the branch commits. A release-triggering title MUST carry a dated `changelog/*.md` entry — the `📓 Changelog completeness` gate in the local `skills` job (`🧩 Skills & changelog`) enforces it (no entry → the job fails). There are no `.changeset/*.md` files any more.
- **Single published package.** npm versioning is repo-level: the root `@rheged-studio/agent-skills` is the only published package (ADR-0002), with `files: ["skills/"]` as the published surface. There is no `pnpm-workspace.yaml` and no `workspaces` field. Skills carry their own **non-npm** version in `SKILL.md` `metadata.version` (mirrored in the skill's private `package.json`), bumped by hand — `pnpm validate:skills` enforces that parity in CI (the `🧩 Validate skill bundle metadata` step in the local `skills` job, `🧩 Skills & changelog`).
- **Skill versioning is non-npm.** Each skill carries its own version in its `package.json` `version` (kept `private: true`) mirrored into `SKILL.md` `metadata.version`, bumped **by hand** per ADR-0001 Decision 2's semver semantics when that skill changes. This label is for consumers/runtime introspection and is decoupled from the root npm release — it is **never** driven by a changeset. See [ADR-0002](architecture/0002-repo-level-npm-versioning.md).
- **Skill bundle metadata contract.** Every `skills/<name>/` ships a `package.json` with `name: "@rheged-studio/skill-<name>"` (the `skill-` prefix + directory name), `private: true`, a semver `version` (starts at `0.1.0`), and `repository.directory: "skills/<name>"`; plus a `SKILL.md` whose `name` equals the directory and whose `metadata.version` **matches** the `package.json` version. Full layout in [ADR-0001 Decision 3](architecture/0001-skill-layout.md). `pnpm validate:skills` enforces the naming/`private`/version + `metadata.version` parity rules in CI (the `🧩 Validate skill bundle metadata` step in the local `skills` job, `🧩 Skills & changelog`); `skills-ref validate` (the `skill-manifests` job) covers the rest of the spec.
- **Trunk config key (intentional divergence).** The diff-based skills name the trunk `baseBranch` (`changelog`, `send-it` — they diff `origin/<baseBranch>...HEAD`); `cleanup-repo` names it `mainBranch` (its merge-detection target — **both** its passes resolve against `origin/<mainBranch>`: `git branch --merged origin/<mainBranch>` for git-ancestry merges, **plus** a `gh pr list --head <branch> --base <mainBranch> --state merged` pass that catches squash-merged branches the ancestry check can't see, since a squash lands a fresh commit whose SHA is never an ancestor of the trunk). The two names reflect the two different roles, so they are **not** converged — `rheged-skills-setup` maps between them when reconciling config. Don't "fix" one to match the other (A-538).
- **Config/example key parity.** The shipped `config.example.json` and this repo's own real config must keep their **key sets identical** (values may differ — the example carries placeholders). Since A-615 the per-skill `config.json` is gitignored (it would otherwise be vendored into consumers by `skills add --copy`), so the real values live in the tracked `infrastructure/dogfood-config/<name>.json` tree — that is what `pnpm validate:skills` compares against each `config.example.json` (A-538). A skill with no dogfood config (e.g. `preflight`, whose config lives at the consumer root) is exempt.

## Shipping changes (`/send-it`)

`/send-it` (the [`send-it` skill](skills/send-it/SKILL.md), dogfooded via the thin `.claude/commands/send-it.md` shim) is the all-in-one ship pipeline: it commits uncommitted work as atomic Conventional Commits, runs the change-gated lint `preflight`, composes a **Conventional Commits PR title** (CI + humans; feature-PR bump after merge comes from landed commit subjects) and writes or updates a dated `changelog/<ts>-<slug>.md` entry for shippable changes, pushes the branch, opens or updates a draft PR, transitions linked Linear issues to **In Review**, and then **chains into `/triage-pr`** (Step 11 — A-1151) to drive the PR to merge-ready: the Phase A CI fix loop, the promote-on-proven-green flip, then Phase B up to triage-pr's human envelope. A default run is therefore unattended for roughly 30 minutes and ends on a `[y/N]` prompt rather than a report. **The triage chain is part of the run, not an optional extra** — `--skip-triage` / `triage: false` exists for the narrow cases where the chain cannot work (a PR that changes the chain itself; `triage-pr` absent; CI gated on `draft == false`), not as a way to finish sooner, and any run that skips it must say why. In this repo `triage: true`, so the chain is on. It is a thin orchestrator that delegates the commit step, lint gate, changelog authoring, Linear writeback, and post-PR triage to the standalone `commit` / `preflight` / `changelog` / `linear-sync` / `triage-pr` skills. It never arms auto-merge — `--merge-when-ready` was removed in send-it 0.8.0 and merging stays a human action. Prefer it over hand-rolled `git commit` + `git push` + `gh pr create` flows. For just the commit step on its own — atomic Conventional Commits with the out-of-scope guard, no push/PR/changelog/Linear — use the standalone [`/commit`](skills/commit/SKILL.md) (dogfooded via `.claude/commands/commit.md`).

Common invocations:

```bash
/send-it                              # commit + changelog + PR title + push + draft PR + triage chain
/send-it --issue=A-132              # same, plus prefix the auto-branch with a-132-
/send-it --ready                      # open the PR ready-for-review (not draft)
/send-it --worktree=<branch-or-path>  # cd into a worktree first, then run
/send-it --base=<branch>              # target a non-main base (stacked PRs)
/send-it --title="fix(x): …"          # override the derived PR title verbatim
/send-it --skip-preflight             # bypass the lint gate (prints a warning)
/send-it --skip-triage                # stop at the open PR (narrow cases only; say why)
```

Because this repo ships many independently-versioned skill bundles, the skill's
`config.json` sets `bundleVersioning`: when a `skills/<name>/` bundle changes without
a version bump, `/send-it` proposes one and (on confirmation) bumps its `package.json`
`version` + `SKILL.md` `metadata.version` in lockstep before composing the PR title.

**`/send-it` is now the shared `send-it` skill (A-389).** The canonical workflow lives in [`skills/send-it/SKILL.md`](skills/send-it/SKILL.md); this repo dogfoods it through the thin `.claude/commands/send-it.md` shim — the same pattern as `/commit`, `/preflight`, `/changelog`, `/linear-sync`, and `/triage-pr`. The deterministic slug/bump helper is the bundle's own zero-dependency `skills/send-it/scripts/derive-bump.mjs` (Node built-ins, no `tsx`; `infrastructure/send-it/` is gone). Consumers install it with `npx skills add … --skill send-it`, alongside the `commit` / `preflight` / `changelog` / `linear-sync` / `triage-pr` skills it delegates to. Rolling the other repos (Octavo + the single-package repos) onto the shared skill and deleting their per-repo copies is the remaining cross-repo work tracked under A-389. The repeatable wipe→install→reconcile→verify mechanism every per-repo migration shares is documented in [`docs/fleet-deployment.md`](docs/fleet-deployment.md), with an `infrastructure/scripts/fleet-wipe.mjs` helper for the wipe step (A-464).

## Release

`.github/workflows/pkg-release.yml` is a **thin caller** of `rheged-studio/shared-workflows`' `reusable-pkg-release.yml` (SHA-pinned `@6cbcab65ca27950387b145888a68dd8e5e0d3ebe # v1.0.0`); it passes `with: { npm-scope }`, grants the permissions superset (`contents`/`id-token`/`issues`/`packages`/`attestations: write`), and owns the `push`-to-`main` trigger (no `workflow_dispatch` — A-326). It is **publish-only** — it never opens or merges the release PR. Versioning is owned by the **Clacks** (`rheged-studio/clacks`) repo running **release-please**, mirroring `@rheged-studio/eslint-config` (A-311 / A-312 / A-320 / A-380). The reusable workflow is a **build-once-publish-exact split** (A-328): an unprivileged build leg (`pnpm install` + `npm pack` — no compile step; agent-skills ships skills.sh bundles) packs one tarball; the npm-OIDC leg and the GitHub-Packages leg (GitHub-native provenance attestation) each download and publish that exact tarball, so the npm tarball, the GitHub Packages tarball, and the attested digest are byte-identical and no build-time code runs alongside a publish credential. Non-secret knobs (node-version-file, registry URLs, npm scope) come from `infrastructure/repo-config.yaml` via `reusable-load-repo-config.yml@v1` (allowlist-validated → outputs, A-330 / A-779). `files: ["skills/"]` in `package.json` scopes the tarball to the skill bundles. Changelog enrichment/finalisation is **not** part of publishing — it runs in its own in-repo `changelog-enrich` job (`reusable-changelog-enrich.yml` + the `@rheged-studio/changelog-core` package; see "How a release flows" below), not in the orchestrator any more (A-797 / A-801). Publishing is dual-registry (public npm + GitHub Packages) and **live**: the root package is public (`private: false`), so each release-PR merge publishes a real version — `1.0.0` and `1.1.0` are on npm. The publish internals live centrally in `reusable-pkg-release.yml` (A-384); this repo no longer ships local `publish-*.sh` wrappers.

### How a release flows

1. A feature PR merges to `main` with a Conventional-Commit title (`feat:`/`fix:`/breaking → release-triggering; `docs`/`chore`/`ci`/… → not). `pkg-release.yml` fires; the reusable workflow's **version-vs-tag gate** sees `package.json`'s version already tagged (`v<version>` exists), so it's a clean no-op.
2. On its 15-minute cron tick the orchestrator mints a short-lived repo-scoped App token (the bot's private key **never** touches this public repo's CI), runs `release-please release-pr` (which reads Conventional Commits on trunk — landed commit subjects after feature merge commits — computes the bump, and bumps `package.json` + `.release-please-manifest.json`), and opens/force-updates the `release-please--branches--main` PR titled `chore(main): release <version>`. The orchestrator **no longer** enriches or finalises the dated `changelog/` entries — that ran centrally as its inline "📝 Finalise" step until A-801 deleted it; post-merge enrichment now runs **in-repo** (see below).
3. The orchestrator waits for the required **`GO/NO GO`** check (the `go-no-go` aggregator job in `validate.yml`, which `needs:` the `config`/`lint`/`build-test`/`skills`/`skill-manifests` jobs and deliberately runs on the release PR), then **squash-merges** it (pinned to the gate-checked head SHA — A-334 / A-1175). Release PRs stay squash even though feature PRs use merge commits.
4. That merge re-fires `pkg-release.yml`. The version-vs-tag gate now sees a freshly bumped, **untagged** version → it runs the publish path: the build leg packs the tarball, then the npm-OIDC leg + the GitHub-Packages leg (provenance attestation) publish that exact artifact, plus an explicit idempotent git tag / GitHub release. The same merge also runs the **in-repo `changelog-enrich` job** (see below), which is what stamps `version` and fills the post-merge fields on the dated `changelog/` entry; the GitHub-release notes are sourced from that entry. The package is public, so both legs publish for real. A `🚨 Notify on release failure` step opens/updates a tracking issue if any step fails (the run is unattended).

- **Post-merge changelog enrich (in-repo, A-797 / A-821).** `pkg-release.yml` carries a `changelog-enrich` job that calls `rheged-studio/shared-workflows`' `reusable-changelog-enrich.yml` (SHA-pinned) with `mode: finalise` — the npm-target mode: it runs `@rheged-studio/changelog-core`'s `finalise` over the dated `changelog/` entries (resolving each merged PR from the entry's `branch:`, filling `merged_at`/`commit`/`pr`/`stats` and stamping the just-bumped `version`), then writes the result back as a path-scoped push by `road-runner-bot[bot]`. It needs `secrets: inherit`. This replaces the orchestrator's deleted inline "📝 Finalise" step and the retired daily `enrich-changelogs.yml` cron (A-801). (`mode: enrich` is the deploy-target variant for repos never checked out during release — not used here.)

- **npm leg.** The publish logic (formerly this repo's `scripts/publish-via-raw-npm.sh`) is now inlined in `reusable-pkg-release.yml` (A-384) — no `changesets/action` shell now that Changesets is gone (A-380), and pnpm's own OIDC path fails even with an upgraded npm on `PATH` (eslint-config A-174). It publishes the prebuilt `$TARBALL` from the build leg via `npm publish "$TARBALL" --access public --provenance` (the upgraded npm), and is idempotent (skips only on a genuine `npm view` hit — exit 0 _with_ output). Auth is OIDC Trusted Publishing — **no `NPM_TOKEN`**. Needs npm ≥ 11.5.1, hence the "Upgrade npm" step (the runner ships npm 10.9.x, which is both too old and broken on self-upgrade). The publish is gated on `push` + `refs/heads/main` + the version-vs-tag gate (`should_publish == 'true'`), alongside the branch-restricted `npm-release` environment (A-326).
- **GitHub Packages leg.** A separate job (so `packages: write` never coexists with the npm OIDC credential). `actions/attest-build-provenance` signs the exact tarball, then the inlined GitHub-Packages publish logic (formerly `scripts/publish-to-github-packages.sh`, now centralised in `reusable-pkg-release.yml` — A-384) publishes it. Gated on the same `should_publish` + main-only condition. It's idempotent against `npm.pkg.github.com`, uses token auth via `GITHUB_TOKEN` (no OIDC; `npm --provenance` is npmjs.org-only, so provenance rides the attestation instead), and hard-codes the registry host, failing closed on drift (A-330).

The retained `infrastructure/scripts/ensure-*.sh` bootstraps are exercised by bats tests in `infrastructure/tests/`, run (alongside shellcheck) via the shared `build-test` reusable caller (`reusable-build-test.yml`) — the old local `infra` job is gone, as are the deleted `publish-*.sh` scripts and their bats. The dated-changelog helpers (the zero-dep `skills/changelog/scripts/*.mjs` bundle — A-369) and the send-it slug/bump helper (`skills/send-it/scripts/derive-bump.mjs`) have vitest unit tests, run in the local `skills` job (`🧩 Skills & changelog`, which needs the `pretest` bootstrap hook the reusable caller's `vitest run` skips). Note the changelog `.mjs` are kept as the **published skill source** (and are still `--self-test`ed here), but this repo's own CI/release no longer shells out to them — validation, the completeness gate, and post-merge finalise all route through `@rheged-studio/changelog-core` (A-797). Workflow YAML/actionlint is linted by the shared `lint` reusable caller (`reusable-lint.yml` — centralised `.yamllint.yml` + actionlint 1.7.12 in shared-workflows), not a local `yaml-lint` job; the `ensure-*.sh` scripts remain as tested local tooling.

### One-time setup (out of band, operator)

The orchestrator model needs server-side config that lives outside this repo:

1. **Add `agent-skills` to the orchestrator matrix** — `strategy.matrix.repo` in `release-orchestrator/.github/workflows/orchestrate-releases.yml` (a separate PR in that repo). This is the only orchestrator-side change; there is no central allowlist file.
2. **Install road-runner-bot** on `agent-skills` with `contents: write` + `pull-requests: write`. Its private key stays scoped to the orchestrator repo — never broaden it here.
3. **Create the `npm-release` environment** restricted to `main` (defence-in-depth, A-326). Without it the workflow still runs — GitHub auto-creates an _unprotected_ environment on first use and publishing stays gated by the explicit `push` + `refs/heads/main` step guards — so this adds the structural branch restriction on top:

   ```bash
   gh api -X PUT repos/rheged-studio/agent-skills/environments/npm-release \
     --input - <<<'{"deployment_branch_policy":{"protected_branches":false,"custom_branch_policies":true}}'
   gh api -X POST repos/rheged-studio/agent-skills/environments/npm-release/deployment-branch-policies \
     -f name=main -f type=branch
   ```

4. **Make `GO/NO GO` a required status check** on `main` (the `go-no-go` aggregator replaces the old `🔬 Build & Lint` check — the orchestrator polls it verbatim); **`pr-title / Validate PR title is a Conventional Commit`** is required too. Add these to a **repo-level** ruleset / branch-protection rule on `agent-skills`, _not_ the org-level "Protect main trunk" ruleset (that governs every org repo). The `go-no-go` job runs on the `release-please--branches--main` PR (no skip), so the orchestrator's release PRs satisfy it. Keep "Allow GitHub Actions to create and approve pull requests" **off**; enable "Allow auto-merge".

> **60-day caveat.** The orchestrator's schedule auto-disables after 60 days with no commits to the orchestrator repo — releases then stop silently. Keep it alive (a periodic commit, or an external cron trigger).

### Flip-to-public checklist (done — kept for reference)

The root package has already gone public and live (`private: false`, first release `1.0.0`, now `1.1.0` on npm). These are the steps that flip was — the one part that was **not** mechanical is the very first publish: it **cannot go through CI** and had to be done by hand (see **Bootstrap publish** below for why and how). npm has no pending-Trusted-Publisher flow, so the package had to exist on the registry _before_ the Trusted Publisher allowlist form was even reachable. Kept here for the next package extracted from this repo.

1. **Set `private: false`** in `package.json`. `publishConfig` (`access: public`, `provenance: true`, registry) is already present. The publish legs stop short-circuiting the moment this flips — they publish on the next version-PR merge.
2. **Land a `feat:`/`fix:` (or breaking) PR** so release-please cuts a version (the bootstrap publish ships at that version).
3. **Manual publish #1** — follow the **Bootstrap publish** runbook below: a hand-driven `npm publish` reserves the name on npm. With the default `auth-type=web`, npm opens a browser and your passkey approves the first-publish 2FA (a recovery-code `--otp` is the headless fallback). This step is unavoidable; bypass-2FA tokens don't work for a brand-new package's first publish.
4. **Configure the npm Trusted Publishing allowlist** at `npmjs.com/package/@rheged-studio/agent-skills/access` → GitHub Actions. The caller workflow filename (`pkg-release.yml`) and the `rheged-studio/agent-skills` repo must match the allowlist entry exactly, or OIDC publish 404s (eslint-config A-174). npm's OIDC subject matches the caller stub filename, not the reusable callee. This is only reachable _after_ step 3.
5. **CI takes over from publish #2.** The next version-PR merge publishes via OIDC (npm) + GitHub Packages + provenance, with no standing `NPM_TOKEN`. The GitHub Packages leg needs no extra config — `packages: write` and `GITHUB_TOKEN` auth are already wired.

`validate.yml` now composes shared reusable callers with a few local jobs:

- **`config`** (`⚙️ Load repo config`) — calls `reusable-load-repo-config.yml@v1` and exposes the repo-config knobs as outputs (A-779).
- **`lint`** — a caller of `rheged-studio/shared-workflows`' `reusable-lint.yml`: ESLint (over the same glob set the old `pnpm lint` covered) + Markdown (markdownlint-cli2, extending the shared `@rheged-studio/markdownlint-config`) + YAML/actionlint. Changelog validation is **not** here — see `skills`.
- **`build-test`** — a caller of `reusable-build-test.yml`: tsc typecheck + ShellCheck + bats. `build: false` (agent-skills ships skills.sh bundles — nothing to compile) and `test: false` (Vitest is local — see `skills`).
- **`skills`** (`🧩 Skills & changelog`) — **local**. Runs `pnpm bootstrap:config` (materialises the gitignored per-skill `config.json` from `infrastructure/dogfood-config/`, A-615), then the Vitest unit tests (`pnpm test`), skill self-tests (`pnpm test:self`), `pnpm validate:changelog` (which runs `changelog-core validate`), `pnpm validate:skills` (the per-skill bundle-metadata guard, A-364), `pnpm vendor:check`, and the `📓 Changelog completeness` gate (A-380 — a `feat`/`fix`/breaking PR title must carry a dated `changelog/` entry; the gate runs `changelog-core check-completeness`). These stay local because they load the per-skill config at runtime and Vitest needs the `pretest` bootstrap hook the reusable caller's `vitest run` skips.
- **`skill-manifests`** (`🧪 Validate skill manifests`) — local; `skills-ref validate` + skill self-tests. Skipped on `release-please--*`.
- **`go-no-go`** (`GO/NO GO`) — **local aggregator**, `needs: [config, lint, build-test, skills, skill-manifests]`, `if: always()`, jq verdict. This is the **required status check** (replacing the old `🔬 Build & Lint`); it runs on the release PR so the orchestrator's release PRs satisfy it.

The Conventional-Commit PR-title lint is a separate workflow, `validate-pr-title.yml` (a thin caller of `reusable-validate-pr-title.yml`, caller job id `pr-title`), not a `validate.yml` job — the title remains the CI/human declaration (and the completeness-gate input); for feature PRs the post-merge bump comes from landed commit subjects (A-1176 / A-824). Required status context `pr-title / Validate PR title is a Conventional Commit`.

The deeper eslint-config hardening that was deferred during the bootstrap — the build-once split + provenance attestation, the `load-repo-config` action, the dated-changelog system, and husky — **landed in [A-345](https://linear.app/rheged-studio/issue/A-345)** ahead of the publishing flip, and the publish path itself is now centralised in `reusable-pkg-release.yml` (A-384). The machinery is fully wired, exercised in CI, and **live** — the package is public (`private: false`), so each release-PR merge publishes for real.

> **The package is public (`private: false`), so the real `pnpm run release:manual` publishes.** (Historically, while the root was `private: true`, `npm publish` errored `EPRIVATE` by design and `release:manual:dry` still simulated a tarball — a green dry-run proved only that the tarball packed and auth worked, not that a real publish was unblocked. That guard no longer applies now that the package is public.)

### Manual publish (break-glass — CI-down only, after the package exists)

> **This is break-glass, not a routine path (A-331).** Reach for it only when CI/OIDC is genuinely down — every normal release goes through `pkg-release.yml` (OIDC, no standing token). The `.env` `NPM_TOKEN` is a long-lived credential, so treat it accordingly:
>
> - **Store it in a secrets manager**, retrieved just-in-time into the shell — not committed to a plaintext `.env` that lingers on disk (`.env` is gitignored, but a secrets manager is the stronger control).
> - **Shortest viable lifetime + a documented rotation cadence**; rotate immediately if a laptop is lost or the token is exposed.
> - It never touches CI (this file forbids `NPM_TOKEN` as a CI secret), and manual publishes are distinguishable from CI ones (no provenance badge), so a manual release can't masquerade as a verified CI one. The only way this token leaks is full local-machine compromise.

For when CI is down. **If you're at an interactive machine, the simplest break-glass is no token at all** — run `pnpm run release:manual` and approve the 2FA in the browser with your passkey (same flow as a bootstrap publish). The `.env` `NPM_TOKEN` path below is for _unattended/headless_ break-glass, where there's no browser to complete the passkey challenge.

Token auth setup (one-time, or after rotating your token):

```bash
NPM_TOKEN=$(grep '^NPM_TOKEN=' .env | cut -d'=' -f2-)
npm config set //registry.npmjs.org/:_authToken "$NPM_TOKEN"
npm whoami    # verify
```

The token must be a **Granular Access Token with the "Bypass 2FA" option enabled at creation time**. Without that flag, every publish hits `EOTP` and you're stuck. Tokens are immutable after creation — if you forgot the flag, revoke and regenerate.

Then publish:

```bash
pnpm run release:manual:dry    # simulate — verifies tarball + auth
pnpm run release:manual        # actual publish
```

`--provenance=false` is intentional — provenance attestation requires a GitHub Actions OIDC issuer, which a laptop doesn't have. Manual publishes ship without the provenance badge; CI publishes get it. (agent-skills has no build step, so `release:manual` is a bare `npm publish` — unlike eslint-config's chained `build && publish`.) Use `release:manual:dry` to simulate rather than passing `--dry-run` through `release:manual`.

### Bootstrap publish — read this when setting up a new package

The very first publish of a brand-new npm package **cannot go through CI**. Two reasons that compound:

- npm (unlike PyPI) has no pending-Trusted-Publisher flow. The package must exist on the registry before the Trusted Publisher form is reachable at `npmjs.com/package/<name>/access`.
- npm enforces 2FA at the publish endpoint for the first publish of a new package, irrespective of account/org/token bypass settings. Granular bypass-2FA tokens only honour the bypass on subsequent publishes.

So bootstrap is always: manual first publish → configure Trusted Publisher → CI takes over from publish #2.

**Pre-flight:**

- You belong to the target npm org with publish rights.
- npm CLI ≥ 11.5.1 (`npm install -g npm@latest`).
- Account has 2FA enabled with a **passkey registered** (preferred — it satisfies the first-publish 2FA in the browser). Have **recovery codes generated and saved** too, as the headless fallback.
- An interactive browser is available and `auth-type=web` is in effect (the npm default — check with `npm config get auth-type`). That's what lets npm hand off the publish 2FA to your passkey.
- `package.json` is at the version you want to ship (release-please's release PR bumps `package.json` + `.release-please-manifest.json`; the in-repo `changelog-enrich` job version-stamps the dated `changelog/` entries via `changelog-core` on merge; for a hand-driven bootstrap, set the version manually or merge the release PR first).

**Sequence:**

1. Get `package.json` to the target version — normally by merging the release-please release PR (which bumps `package.json` + `.release-please-manifest.json`; the in-repo `changelog-enrich` job then finalises the dated `changelog/<ts>-<slug>.md` entries via `changelog-core` on merge). There is no root `CHANGELOG.md` (release-please runs with `skip-changelog`); the dated entries are the only changelog.
2. `pnpm run release:manual:dry` — verify tarball + auth. **Note:** dry-run does NOT trigger 2FA enforcement, so a successful dry-run does not predict a successful real publish. It only proves the tarball is valid and your credentials authenticate.
3. `pnpm run release:manual` — the real publish. With `auth-type=web` (the npm default) npm **opens a browser and prompts for 2FA; approve it with your passkey** (Touch ID / Face ID / security key). That satisfies the first-publish 2FA and the package publishes — no `--otp`, no recovery code. This is the normal path on current npm.
4. **Fallback — only if the browser flow isn't available** (headless host, no passkey registered, or an npm too old for web auth): the publish stops at `EOTP`. Pass a **recovery code as the `--otp` value**:

   ```bash
   npm publish --access public --provenance=false --otp=<recovery-code>
   ```

   Generate codes at npmjs.com → Profile → Two-Factor Authentication → Manage Recovery Codes. Each is single-use. The format is a long hex string (not a 6-digit TOTP) — npm accepts it as `--otp` anyway. **If you use one, immediately regenerate recovery codes** — the one you used is burnt; if you transmitted it anywhere (chat, paste buffer with cloud sync, screen share), treat the rest of the set as compromised. (The passkey path in step 3 burns nothing, so there's nothing to regenerate.)

5. Configure Trusted Publisher: `https://www.npmjs.com/package/@rheged-studio/agent-skills/access` → GitHub Actions → org, repo, workflow filename (`pkg-release.yml` — the caller stub, which is what npm's OIDC subject matches, not the reusable callee), environment `npm-release`.
6. From here on, releases go through CI cleanly.

#### Fallback troubleshooting — things that look like solutions but aren't

These only matter when you're on a headless host (or have no passkey) and stuck on `EOTP` — on an interactive machine the passkey browser flow (step 3) just works and you skip all of this. When you _are_ stuck, a recovery-code `--otp` (step 4) is the answer; these are **not**:

- Toggling "Require 2FA for write actions" off in account settings.
- Disabling org-level 2FA enforcement.
- Generating a Granular token with bypass-2FA enabled — works for publish #2+, NOT publish #1.
- `oathtool` for generating TOTP — only works if you have a TOTP secret, and **npm has phased TOTP out of new accounts** (only passkeys + recovery codes are offered now).
- Disabling 2FA entirely — npm's policy _requires_ either 2FA or a bypass-2FA token; you can't disable both. And the bypass token doesn't help for publish #1 anyway.

> **Don't disable `auth-type=web` reaching for a recovery code.** `auth-type=web` is the npm default and is precisely what lets a passkey satisfy the publish 2FA in the browser — it is the _primary_ path (step 3), not a dead-end. Recovery codes only become "the answer" when no browser/passkey is in play.
